# 瓜瓜拼车 V1.1 设计：校园可信、基础匹配与管理员治理

日期：2026-05-05  
状态：待用户审阅  
范围：在已跑通的瓜瓜拼车 MVP 上新增可信认证、相似行程推荐和小程序内管理员治理能力。

## 1. 背景

当前 MVP 已具备：广场列表、发布行程、详情页、查看联系方式、我的行程状态管理、举报、云函数与基础数据库集合。V1.1 的目标不是把产品做成网约车平台，而是让它更适合作为西北工业大学校内拼车信息撮合工具使用。

V1.1 继续坚持边界：只做同学校内行程信息撮合，不做支付、不做抽佣、不做司机接单、不做自动派单、不做车主资质认证。

## 2. 产品目标

V1.1 要解决三个核心问题：

1. 可信：未认证用户不能发布，也不能查看联系方式。
2. 好找人：在详情页和发布成功后推荐 90 分钟内的相似行程。
3. 可治理：管理员能审核认证、处理举报、拉黑用户，拉黑后自动隐藏该用户的 open 行程。

## 3. 非目标

V1.1 明确不做：

- 支付、押金、分账、抽佣。
- 司机接单、车主认证、网约车经营能力。
- 实时聊天。
- 路线订阅提醒。
- 邮件验证码真实发送服务接入。
- 学生证、校园卡、身份证等图片上传审核。

邮箱认证入口和数据结构会预留，但 V1.1 的真实可用认证方式先以人工审核为主。

## 4. 用户角色与权限

### 4.1 未认证用户

- 可以浏览广场。
- 可以查看行程详情。
- 不能发布行程。
- 不能查看联系方式。
- 点击发布或查看联系方式时，引导进入校园认证页。

### 4.2 审核中用户

- 可以浏览广场和查看详情。
- 不能发布行程。
- 不能查看联系方式。
- 点击受限动作时提示“认证审核中，通过后可使用”。

### 4.3 已认证用户

- 可以发布行程。
- 可以查看联系方式。
- 可以管理自己的行程状态。
- 对外显示“西工大认证”。

### 4.4 被拉黑用户

- 不能发布行程。
- 不能查看联系方式。
- 其所有 open 行程在拉黑时自动隐藏。
- 解除拉黑后恢复发布和查看联系方式权限，但不会自动恢复已隐藏行程。

### 4.5 管理员

管理员由数据库 `users.role = "admin"` 指定。管理员在“我的”页看到管理员入口，普通用户不可见。管理员可以：

- 审核认证申请。
- 处理举报。
- 搜索和管理用户。
- 拉黑或解除拉黑用户。

## 5. 页面设计

### 5.1 我的页

新增认证状态卡片：

- 未认证：显示“未认证”，主按钮“去校园认证”。
- 审核中：显示“认证审核中”。
- 已认证：显示“西工大认证”。
- 认证失败：显示失败原因，允许重新提交。
- 被拉黑：显示“账号受限”，隐藏发布入口或提示受限原因。

若当前用户是管理员，显示“管理员入口”。

### 5.2 校园认证页

新增页面 `pages/verify/verify`。

页面分两个区域：

1. 邮箱认证
   - 展示 `@mail.nwpu.edu.cn` 邮箱认证说明。
   - V1.1 暂不真实发送验证码。
   - 按钮显示为“即将支持”或置灰提示。

2. 人工审核
   - 学号。
   - 姓名。
   - 学院。
   - 年级。
   - 备注，可选。

提交后创建 `verificationRequests` 记录，并将用户 `verifyStatus` 更新为 `pending`。

### 5.3 管理员页

新增页面 `pages/admin/admin`，仅管理员可进入。后端云函数仍需校验管理员权限，不能只依赖前端隐藏。

管理员页包含三个 tab：

1. 认证审核
   - 查看待审核申请。
   - 查看学号、姓名、学院、年级、备注。
   - 通过认证。
   - 拒绝认证并填写拒绝原因。

2. 举报处理
   - 查看举报列表。
   - 查看被举报行程摘要。
   - 一键隐藏违规行程。
   - 标记举报已处理。

3. 用户管理
   - 按昵称、openid 后 6 位、认证状态搜索用户。
   - 查看用户认证状态、角色、拉黑状态、最近发布数量、最近被举报次数。
   - 拉黑用户，填写原因。
   - 解除拉黑。

### 5.4 详情页相似行程推荐

在详情页底部新增“相似行程”区域：

- 最多展示 3 条。
- 每条展示路线、时间、人数、发布者认证状态、查看详情按钮。
- 当前用户无认证也可看推荐摘要，但仍不能查看联系方式。

### 5.5 发布成功后的推荐

已认证用户发布成功后调用相似行程推荐：

- 若有相似行程，提示“已发布，发现 N 个相似行程”。
- 用户可选择去查看推荐或返回广场。
- 若没有相似行程，保持现有成功提示。

## 6. 数据模型

### 6.1 `users` 扩展

```js
{
  _id: "openid",
  openid: "openid",
  nickname: "同学",
  avatarUrl: "",
  role: "user", // user | admin

  verified: false,
  verifiedLabel: "未认证", // 未认证 | 审核中 | 西工大认证 | 认证失败
  verifyStatus: "unverified", // unverified | pending | verified | rejected
  verifyMethod: "", // manual | email | ""
  rejectReason: "",

  blocked: false,
  blockedReason: "",
  blockedAt: null,
  blockedBy: "",

  createdAt: 1777480000000,
  updatedAt: 1777480000000
}
```

### 6.2 新集合 `verificationRequests`

```js
{
  _id: "cloud id",
  userOpenid: "openid",
  studentId: "2024000000",
  realName: "张三",
  college: "计算机学院",
  grade: "2024",
  note: "",
  status: "pending", // pending | approved | rejected
  rejectReason: "",
  reviewedBy: "admin openid",
  reviewedAt: null,
  createdAt: 1777480000000,
  updatedAt: 1777480000000
}
```

每个用户同一时间只允许存在一个 pending 申请。被拒绝后可以重新提交，保留历史记录。

### 6.3 `reports` 扩展

```js
{
  tripId: "trip id",
  reporterOpenid: "openid",
  reason: "black_car_risk",
  detail: "疑似黑车引流",
  status: "open", // open | reviewed | rejected
  resolutionNote: "",
  resolvedBy: "admin openid",
  resolvedAt: null,
  createdAt: 1777480000000,
  updatedAt: 1777480000000
}
```

### 6.4 `trips` 状态约定

沿用现有状态：

```js
open | full | cancelled | expired | hidden
```

管理员拉黑用户时，将该用户所有 `status = "open"` 的行程更新为 `hidden`。

## 7. 云函数设计

### 7.1 新增云函数

#### `verificationSubmit`

用户提交人工认证申请。

职责：

- 确保用户存在。
- 校验用户未被拉黑。
- 校验学号、姓名、学院、年级。
- 限制同一用户只能有一个 pending 申请。
- 创建 `verificationRequests`。
- 更新 `users.verifyStatus = "pending"` 和 `verifiedLabel = "审核中"`。

#### `verificationList`

管理员查看认证申请列表。

职责：

- 校验管理员权限。
- 支持按状态筛选，默认 pending。
- 按创建时间倒序返回。

#### `verificationReview`

管理员审核认证申请。

职责：

- 校验管理员权限。
- 支持 `approve` 或 `reject`。
- 通过时更新申请状态为 approved，并更新用户为已认证。
- 拒绝时更新申请状态为 rejected，并更新用户为 rejected 和拒绝原因。

#### `adminReportList`

管理员查看举报列表。

职责：

- 校验管理员权限。
- 支持按状态筛选。
- 返回举报信息和被举报行程摘要。

#### `adminReportResolve`

管理员处理举报。

职责：

- 校验管理员权限。
- 支持标记 reviewed 或 rejected。
- 可选隐藏相关行程。
- 写入处理人、处理时间和处理备注。

#### `adminUserList`

管理员搜索和查看用户。

职责：

- 校验管理员权限。
- 支持按昵称、openid 后 6 位、认证状态、拉黑状态筛选。
- 返回用户基础信息和统计摘要。

#### `adminUserBlock`

管理员拉黑或解除拉黑用户。

职责：

- 校验管理员权限。
- 禁止拉黑自己。
- 拉黑时写入 `blocked` 字段和原因。
- 拉黑时隐藏该用户所有 open 行程。
- 解除拉黑时恢复用户权限，但不恢复已隐藏行程。

#### `tripSimilar`

查询相似行程。

职责：

- 接收 `tripId` 或行程草稿。
- 查询同路线、90 分钟内、状态 open 的行程。
- 排除当前行程。
- 最多返回 3 条公开行程信息。

### 7.2 调整已有云函数

#### `userEnsure`

补齐默认字段：

- `verifyStatus`
- `verifyMethod`
- `rejectReason`
- `blocked`
- `blockedReason`
- `blockedAt`
- `blockedBy`

避免老用户缺字段导致判断异常。

#### `tripCreate`

新增权限校验：

- 被拉黑用户禁止发布。
- 未认证、审核中、认证失败用户禁止发布。
- 只有 `verifyStatus = "verified"` 且 `blocked = false` 的用户可以发布。

#### `contactView`

新增权限校验：

- 被拉黑用户禁止查看联系方式。
- 未认证、审核中、认证失败用户禁止查看联系方式。
- 只有已认证用户可以查看联系方式。
- 继续写入 `contactViews` 审计记录。

#### `tripList`

保持广场只展示 open 行程。后续实现可在查询结果中补充发布者认证状态，避免前端依赖用户集合直查。

#### `tripUpdateStatus`

保持只有发布者本人能修改自己的行程状态。管理员隐藏行程走 `adminReportResolve` 或后续专用管理函数，不复用普通用户状态更新入口。

## 8. 相似行程推荐规则

推荐窗口为 90 分钟。

优先级：

1. 强匹配：出发地相同、目的地相同、出发时间差不超过 90 分钟。
2. 弱匹配：V1.1 暂不展示弱匹配，避免误导用户。若强匹配较少，后续版本再扩展。

排序：

1. 时间差越小越靠前。
2. 同等时间差下，创建时间新的靠前。

返回字段不包含联系方式：

- `_id`
- `from`
- `to`
- `earliestTime`
- `latestTime`
- `peopleCount`
- `ownerNickname`
- `ownerVerified`
- `ownerVerifiedLabel`
- `note`

## 9. 错误处理与安全

- 所有管理员云函数必须在云函数内校验 `users.role = "admin"`。
- 所有受限动作必须在云函数内校验认证和拉黑状态，前端只做体验提示。
- 所有公开列表和推荐接口不得返回联系方式。
- 人工认证不上传图片，减少隐私风险。
- 认证申请字段只用于校内身份判断，不在公开页面展示。
- 拉黑操作必须记录原因、管理员 openid 和时间。
- 管理员拒绝认证和处理举报时允许填写备注，方便后续追溯。

## 10. 测试计划

### 10.1 单元测试

新增或调整测试覆盖：

- 用户权限判断：未认证、审核中、已认证、被拉黑。
- 认证申请字段校验。
- 管理员权限校验。
- 拉黑后隐藏 open 行程的状态变更逻辑。
- 相似行程 90 分钟匹配和排序。
- `contactView` 对未认证和被拉黑用户的拒绝。
- `tripCreate` 对未认证和被拉黑用户的拒绝。

### 10.2 手动验收

1. 未认证用户可以浏览广场和详情。
2. 未认证用户不能发布。
3. 未认证用户不能查看联系方式。
4. 用户提交人工认证后变为审核中。
5. 审核中用户仍不能发布和查看联系方式。
6. 管理员通过认证后，用户可以发布和查看联系方式。
7. 管理员拒绝认证后，用户看到拒绝原因并可重新提交。
8. 管理员可以查看举报并隐藏违规行程。
9. 管理员拉黑用户后，该用户不能发布和查看联系方式。
10. 管理员拉黑用户后，该用户所有 open 行程从广场消失。
11. 解除拉黑后，用户恢复权限，但已隐藏行程不自动恢复。
12. 详情页展示 90 分钟内同路线相似行程。
13. 发布成功后，如存在相似行程，出现推荐提示。

## 11. 分阶段实施建议

V1.1 可以拆成三批：

1. 认证与权限门禁
   - 用户字段扩展。
   - 人工认证提交和审核。
   - 发布、查看联系方式权限限制。

2. 管理员治理
   - 管理员入口和管理员页。
   - 举报处理。
   - 用户管理和拉黑。

3. 相似行程推荐
   - `tripSimilar` 云函数。
   - 详情页推荐列表。
   - 发布成功后的推荐提示。

每批都应保持小程序可运行，并通过测试后再进入下一批。
